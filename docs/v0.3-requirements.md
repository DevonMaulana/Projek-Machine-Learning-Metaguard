# MetaGuard v0.3 Requirements Research

## Problem and goals

MetaGuard v0.2.0 has a strong generic CSV-quality pipeline, but its contextual
profile is hard-coded as `healthcare` in the Streamlit flow and the agent
execution context. Its policy corpus is government-generic. v0.3 should make
domain/context selection explicit, preserve deterministic-first behavior, and
route only suitable local policy packs.

Goals:

- retain generic quality behavior and v0.2 scoring semantics;
- support extensible profiles: Generic, Healthcare, Education, Environment;
- make rule activation, provenance, policy routing, and evidence alignment
  auditable;
- preserve one bounded orchestrator, human-approved Gemini, and deterministic
  traceability.

## Non-goals

- No runtime LLM domain detection, rule generation, legal conclusion, or
  automatic data correction.
- No multi-agent framework, external policy download, graph database, or new
  embedding model.
- No assumption that a policy mentioning a domain establishes a domain rule.

## Current v0.2 coupling to preserve or isolate

- `run_quality_checks`, `profile_dataframe`, `calculate_score`, and CSV modes
  are generic core behavior.
- `validate_metadata` assumes government/public-data metadata expectations.
- `run_contextual_validation` defaults to `profile="healthcare"`.
- `app.py` explicitly calls contextual validation with `profile="healthcare"`.
- `AgentExecutionContext.contextual_profile` defaults to `healthcare`.
- `HEALTHCARE_RULES` contains occupied-bed/capacity and internet/bandwidth.
  Internet/bandwidth merits later research as generic infrastructure/governance,
  but its v0.2 semantics must not be changed during requirements work.
- Evidence, sufficiency, Gemini, traceability, report, and fingerprint/reset
  retain their existing JSON-safe contracts.

## Analysis context and domain profile

The user must explicitly choose governance context (`government_public` or
`generic_non_government`) and domain (`generic`, `healthcare`, `education`,
`environment`, or `other`). The selection becomes active analysis configuration
and is part of the fingerprint/reset boundary.

Use independent layers rather than one flat enum:

1. generic data-quality layer;
2. optional governance layer;
3. optional domain semantic layer.

An immutable, JSON-safe profile should expose:

```text
domain_id, display_name, description, enabled_rule_packs,
enabled_policy_packs, evidence_need_ids, metadata_expectations,
semantic_concept_ids, optional_configuration, fallback_message
```

Behavior: Generic enables generic quality plus optional governance; Healthcare,
Education, and Environment add their domain packs; Other retains generic checks
and reports that no domain-specific validation profile is active.

## Semantic concept registry

Column matching uses curated aliases and exact normalized matching only. No
unconstrained fuzzy matching or runtime LLM aliases are allowed.

```text
concept_id, domain_id, canonical_name, aliases,
expected_data_type, unit_expectation, description
```

Example design placeholders: future `student_count` may curate `jumlah_siswa`,
`jml_siswa`, `total_siswa`, `peserta_didik`; future `ph_measurement` may curate
`ph`, `ph_air`, `nilai_ph`, `derajat_keasaman`. Provenance and tests are
required before aliases become active.

## Domain rule registry and provenance

Rules remain allowlisted Python functions, not executable formula strings.

```text
rule_id, domain_id, name, description, severity, rule_type,
required_concepts, optional_concepts, evaluator_reference,
policy_requirement, policy_reference, interpretation_note,
human_review_required, provenance_type
```

Rule packs separate generic data rules, governance contextual rules, and domain
semantic rules. Finding provenance must state rule ID, active domain, resolved
concept/column mapping, rule type, policy reference when present, and review
need. Use `DETERMINISTIC_INVARIANT`, `POLICY_SUPPORTED`,
`TECHNICAL_STANDARD`, or `HEURISTIC`; heuristics are never regulations.

The v0.2 bed rule can migrate unchanged as an allowlisted evaluator requiring
the concepts `occupied_beds` and `inpatient_capacity`.

## Policy packs and routing

Current policy baseline is one `government_generic` pack. Policy metadata must
distinguish governance policy, sectoral regulation, technical standard, and
guideline/reference rather than assigning equal legal weight.

```text
policy_id, title, policy_pack, domain_id, authority, document_type,
year, effective_status, source, topics, scope, local_file, revision_info
```

Routing is selected domain + governance context + evidence need + policy
pack/document type. A domain issue may use its domain pack plus
`government_generic` when governance is relevant.

For the current laptop-local codebase, prefer one Chroma collection with
primitive metadata filtering when its query contract supports it. This avoids
multiple model loads and simplifies persistence. Multiple collections per pack
are a later option if corpus size, isolation, or filtering behavior requires it.

## Evidence needs and sufficiency

v0.2 needs are `metadata_governance`, `data_quality`, and `accountability`.
Keep these as governance needs. Add curated domain/technical needs only when an
active rule actually requires support.

Do not create one opaque combined score. Record separate dimensions:

- retrieval coverage status;
- unique-evidence adequacy and source diversity;
- policy-pack/domain alignment;
- overall retrieval readiness for Gemini.

This is never a compliance, legal sufficiency, semantic truth, or correctness
score. Alignment only says routed evidence belongs to the selected pack/context;
it does not validate the interpretation.

## Gemini, traceability, report, and UI

Gemini input should add selected domain/context, active profile/rule packs,
generic/governance/domain findings, rule provenance, policy evidence,
retrieval-readiness dimensions, sampling scope, and limitations. Gemini remains
an interpreter/summarizer/recommendation assistant; it cannot create technical
findings or legal conclusions. Human approval remains mandatory.

Traceability should extend deterministic links from Gemini citation to chunk,
document, policy pack, selected domain, and evidence need. No second LLM review
is required.

Candidate additive report fields: `analysis_context`, `selected_domain`,
`active_rule_packs`, `domain_findings`, `rule_provenance`, `policy_routing`,
`policy_packs`, and `domain_evidence_alignment`. They can remain additive only
if all v0.2 fields are preserved; a concrete consumer-contract review must
precede any schema decision.

Minimal UI flow:

```text
CSV upload → ingestion settings → metadata → analysis context/domain
→ deterministic analysis → contextual/domain findings → retrieval/readiness
→ explicit Gemini approval → traceability → report
```

The UI must show active rule/policy packs and their reason for activation.

## Safe fallback and backward compatibility

If no profile is available, select `other`/`generic`, retain ingestion,
profiling, generic quality checks, scoring, and selected governance behavior,
and show: “No domain-specific validation profile is active.” Domain semantic
conclusions and domain-only policy routing are disabled.

v0.3 must preserve v0.2 generic findings/scoring, exact/chunked/sampled
semantics, fingerprint reset, bounded retrieval, Gemini approval, deterministic
traceability, JSON-safe state, and the absence of automatic legal conclusions.

## Acceptance criteria

Use Generic, Healthcare, Education, and Environment synthetic fixtures. Each
profile must verify active/inactive packs, no cross-domain rule leakage, rule
provenance, appropriate policy routing, evidence alignment, unchanged generic
core, deterministic rerun, reset on domain change, Gemini approval/sufficiency
guards, deterministic traceability, and JSON-safe reports.

## Recommended implementation roadmap

1. Context/domain models and profile registry, with no behavior migration.
2. Semantic concept registry and exact-match tests.
3. Rule registry plus healthcare migration preserving v0.2 semantics.
4. UI/context state and fingerprint integration.
5. Policy registry and metadata-aware routing.
6. Multi-dimensional retrieval readiness/alignment.
7. Education and environment pilot packs after policy/standard research.
8. Provenance/report integration and cross-domain acceptance regression.

Each phase must be small, reversible, testable, and avoid a big-bang rewrite.
